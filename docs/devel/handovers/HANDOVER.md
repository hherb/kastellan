## Current state

**PR (OPEN) — `fix/458-operator-env-overlay`, closing [#458](https://github.com/hherb/kastellan/issues/458).** `kastellan-cli install` regenerates `kastellan.env` from CLI flags on every deploy, so hand-added keys are dropped and tuned values revert — **silently**. On 2026-08-08 that had already cost the deployed bot its whole mail capability for two days: `KASTELLAN_MAIL_ENDPOINT` gone ⇒ `mail.*` never registered ⇒ the planner fell back to `shell-exec` filesystem probing ⇒ the bot answered *"I do not have permission to access your files"*. No code defect anywhere; the only symptom was a wrong answer. Six things worth carrying:

1. **The design rests on a measurement, not a memory.** `EnvironmentFile=` **overrides** `Environment=`, later files win, and `-<missing>` starts fine — verified on the DGX with a transient unit. Hence a second file listed *after* the generated one fixes lost keys **and** reverted values with one mechanism. It also means the regenerated env file **can override the unit's own** `Environment=KASTELLAN_EGRESS_FORCE_ROUTING=1`, which is why the force-routing notice is in scope.
2. **`ServiceSpec.environment_file: Option<PathBuf>` → `environment_files: Vec<EnvFileRef{path, optional}>`.** `optional` must be a real field, not a convention: launchd's `fs::read_to_string(...)?` hard-errors on absence, and `kastellan.env.local` normally does not exist. systemd renders `-`-prefixed directives; launchd folds the files into the plist in the same order.
3. **The `cfg`-free grammar lift paid off measurably.** `parse_env_file`/`merge_env` moved out of the macOS-only `launchd_agents::builders` into `supervisor/src/env_file.rs`. The DGX gate came in at **3069 vs a predicted 3067** — investigated rather than accepted, and the +2 is exactly those two tests **running on Linux for the first time**. They had never compiled on the DGX or in CI. That is the #511 `atomic_write` argument, empirically confirmed.
4. **Install now names what it destroys and keeps a copy.** Pure `diff_env_files` + `kastellan.env.bak` (written only when the diff is non-empty, so a later clean install cannot clobber the one that mattered) + key names only, never values — the operator reads values from the backup, keeping anything secret-shaped out of the install transcript.
5. **Five of the six review findings were defects in the PLAN TEXT**, transcribed faithfully by implementers, none catchable by test counts or clippy. The worst: `diff_env_files` compared a repeated key's *first* value where systemd (and our own `merge_env`) take the *last* — so `old=A=1\nA=2`, `new=A=1`, a genuine revert, was reported as **nothing at all**. Precisely the silent loss the feature exists to surface. [[plan-text-is-a-defect-source]] at scale; the per-task reviewers were the only thing that found them.
6. **The whole-branch review found what per-task reviews structurally could not** — three cross-task defects: `README.md` still taught "edit `kastellan.env` and restart"; `upgrade_from_git.sh` could not read the overlay it now recommends (so following our own warning broke the upgrade script); and `uninstall --purge` destroys the overlay + backup while the daemon's own guidance recommends `--purge`.

**Live-accepted on the DGX, not just gated** (2026-08-09): with the tuned settings in **both** files, one install printed `dropped:` for all four keys + `changed:` for the model tag, wrote the backup, left the overlay's mtime untouched — and `/proc/<MainPID>/environ` then carried **all four keys plus the `-ctx64k` tag and `FORCE_ROUTING=1`**. The exact sequence that killed mail on 2026-08-06, survived.

**PR [#526](https://github.com/hherb/kastellan/pull/526) — MERGED 2026-08-06 as `5cbab01e`, closing [#523](https://github.com/hherb/kastellan/issues/523) and [#524](https://github.com/hherb/kastellan/issues/524)** (branch `fix/523-524-boot-failed-rate-gate`, 6 commits `f58e8474`→`ffb331db`, squashed; spec `docs/superpowers/specs/2026-08-06-boot-failed-rate-gate-design.md`). #523: in the flap band each stable death clears the escalator (`Outage::Ends` → `record_success`), so a transiently-failing restart attempt was evaluated against a freshly-cleared latch — one ungated `channel.boot_failed` row per cycle, unbounded, in exactly #522's regime. Fix: `ReportingPolicy` gains a second `RespawnRateAlarm` on the failed-attempt stream (same `FLAP_ALARM_*` constants as the death alarm). Four things worth carrying:

1. **Read-after-record by construction, not by exception.** The issue's named trap was OR-ing a bare `deaths.in_storm()` read into the attempt gate; feeding a *dedicated* alarm from `note_failed_attempt` itself makes the stale-latch hazard structurally unrepresentable — the only `attempts` accesses in the crate are the record, the read two lines below it, and the test builder. Mutation-pinned: reordering the read fails exactly `the_first_failed_attempt_after_the_attempt_storm_clears_is_recorded`.
2. **The rate gate is deliberately SILENT** — no new log line, no new operator phrase (hence no new #524-class drift surface). Its firing rate cannot distinguish an outage from a flap (~59 attempts/hour in both), so any line would be noise in one regime; each regime already has its loud line. This weakens #518's "the row and the loud line are the same decision" to: every loud line still has its row; rate-gate rows are line-less `cause` samples. Owned in the module doc.
3. **The deferral is what keeps #518's shape intact.** The rate voice keeps a row only while the escalator has NOT escalated — otherwise a sustained outage writes two near-duplicate rows per 30 min (both alarms repeat on independent clocks anchored ~4.5 min apart). Mutation-pinned: dropping `!escalated` fails exactly `a_rate_alarm_repeat_defers_to_an_escalated_outage`. Row arithmetic: 24 h outage ~57 → **~53** (attempts 6–10 between the rate latch at ~15 s and the 5-min escalation are the only loss); flap-with-failing-restarts **unbounded → first 5 + one `cause`-bearing row per 30 min**; plain flap unchanged.
4. **#524 in one move:** `CHANNEL_STILL_DOWN_LOG_PHRASE` const in `boot_supervisor.rs`, interpolated into `report()`'s `error!` and (via `@@CHANNEL_STILL_DOWN@@`) the help block, asserted through the const — every operator phrase in that help block is now const-driven.

**PR [#525](https://github.com/hherb/kastellan/pull/525) — MERGED 2026-08-06 as `4e215481`, closing [#518](https://github.com/hherb/kastellan/issues/518) and [#522](https://github.com/hherb/kastellan/issues/522)** (branch `fix/518-522-channel-event-reporting-gates`, squashed). One predicate now gates the durable audit row for each recurring channel event, driven by the alarm that owns its regime: `DowntimeEscalator` for `channel.boot_failed`, and a new supervisor-owned `RespawnRateAlarm` for `channel.died`. Six things worth carrying:

1. **"Until the alarm speaks" beat #518's own sketch** (`failures <= FIRST_ATTEMPTS_ALWAYS_AUDITED || escalated`). It needs no new constant — N falls out of the escalation threshold and the backoff schedule — and it makes the row and the loud line the *same* decision rather than two that agree today. `should_record(alarm_latched, alarm_spoke_now) = !latched || spoke`, three lines, one truth table, two call sites.
2. **Both latch reads happen AFTER the recording call, and that is the subtle half.** Reading `in_storm()` *before* `record()` reads more naturally and is wrong: when a storm clears, `record()` prunes the window and re-arms, so the first death of the *next* storm reads `false` afterwards (correctly recorded) but `true` beforehand — silently suppressing the one row that says a fresh storm started. `the_first_death_of_a_fresh_storm_is_recorded` pins it; the mutation was run.
3. **`channel.started` was gated, and that was a design error caught mid-branch.** The latch is only ever cleared by a *later death*, so the start that **ends** a storm was suppressed too — and a channel that recovered for good never wrote another row, leaving `channel.died` as the last durable event for a healthy channel. It is now ungated. Cost: a 24 h flap writes ~1470 rows rather than ~58. Worth it — the unbounded-forever case is the sustained *bring-up* outage (a permanently-`Retry` condition such as a missing worker binary, which can persist for weeks), and the `boot_failed` gate fixes that regardless; a flap is loud and short-lived by design.
4. **#522's own premise about `PersistentWorker` is wrong, and so was this branch's first draft of the doc.** `persistent.rs:167` builds the alarm on the driver thread *before* the job loop, and `:220`'s `mem::replace` swaps the *transport* — so it **does** accumulate across worker respawns. What it cannot see is a **channel** restart, which tears down the whole `PersistentWorker`, thread and alarm together. Conclusion unchanged (the channel's alarm must live in the policy, above the thing a restart replaces); attribution corrected. **Check what a dependency actually does before writing why it is wrong** — the same lesson #521 learned about `PgListener`.
5. **#516's finding recurred inside the change that documents itself as immune to it.** `CHANNEL FLAPPING` shipped as a bare literal in `render_email_help` while its own const's doc comment says a const exists "rather than a literal typed twice". The spec had predicted "no new action name, so the guard needs no change" — true, and beside the point: the guard iterates *actions* and this was a *log phrase*. Caught by the final whole-branch review. **A guard protects the category it enumerates and nothing adjacent to it.**
6. **The loud line no longer sits behind the audit write.** `report()` now runs *before* the gated `emit().await`. The reachable cause of a pump death is Postgres going away, and `emit` inherits sqlx's pool-acquire timeout — so the alarm was delayed by exactly that timeout in the case it most matters ([#515](https://github.com/hherb/kastellan/issues/515) territory, one arm of it removed for free).

Row counts: a 24 h sustained bring-up outage goes 1440 → **~57**. A 24 h flap at 61 s cycles goes ~2832 → **~1470**. A transient blip — the common case — is recorded exactly as before, because the gate only engages once an alarm has already spoken.

**PR [#521](https://github.com/hherb/kastellan/pull/521) — MERGED 2026-08-05 as `3932672a`, closing [#517](https://github.com/hherb/kastellan/issues/517), and DEPLOYED the same day.** #516 made *bring-up* supervised; its `Started` arm then parked on the shutdown oneshot and never re-examined the channel. Every `ChannelBus` pump has a terminal exit that nothing watched — the completed-task pump returning when its listener gives up (replies stop going out), a per-channel task breaking on a closed `recv` (inbound stops coming in), or a **panic** in either — and each produces #514's exact signature after boot instead of during it: units `active`, Postgres healthy, log silent, no row. Five things worth carrying:

1. **The premise in the issue was wrong, and it changed the fix.** `PgListener::recv()` **already auto-reconnects** in sqlx 0.9 (`sqlx-postgres/src/listener.rs`), so the `Err` arm is a *failed reconnect* — a sustained Postgres outage — not a dropped connection. The issue's smaller alternative ("make `next_completed` reconnect") would have fixed nothing sqlx does not already do, and could not cover a panic either. **Check what a dependency already does before patching around it.**
2. **A full restart is only safe because teardown is RAII.** `ChannelBus::shutdown` aborts the pump tasks; aborting drops the boxed `Channel`, `MatrixChannel`'s drop closes both driver endpoints, the driver thread exits and its `PersistentHandle` drop tears down worker **and** sidecar. So the loop stops the channel on **both** exits from the wait — abandoning a half-dead bus would leak exactly what #502 fixed.
3. **The flap guard is not optional.** Resetting the failure counter on every `Started` would make a channel that dies on arrival restart at full speed forever, spawning a sandboxed worker per iteration — worse than the deafness being fixed. Only an uptime ≥ 60 s (`DowntimeEscalator::ran_long_enough`, deliberately the backoff cap) resets it; anything shorter stays inside the current outage, so the backoff keeps growing and the escalator keeps counting.
4. **`Drop` is the signal, not a line after the pump body** (`channel/pump_liveness.rs`). Only `Drop` also fires on a panicking or aborted task, which is the whole point — the exits nobody enumerated are the ones that bite. And `Notify::notify_one`, not `notify_waiters`, so a death that precedes the waiter is not lost; the resulting bug would have been "deaf only when the death is fast".
5. **A test that passes in RED is not a test yet.** `a_death_racing_shutdown_…` passed *before* the implementation and *with the `biased` arms reversed*, because `wait_or_shutdown` already declines the restart a few lines later. What the bias actually prevents is a `channel.died` row written for a channel that was merely being shut down — the test now asserts the absent row and fails on mutation, which is the only version that was ever worth having.
6. **Review round (2026-08-05) — one real defect, and it was in the half nothing could observe.** `escalate_if_due` ran on *both* death arms, so a stable death did `record_success()` and then immediately `record_failure()`, opening an outage dated at the death. **Nothing ever closed it**: the escalator learns about health only when a *stable* channel dies, so a channel that came straight back and worked for hours still carried that instant, and the next flap reported every healthy hour as downtime — in the one line whose text asserts nothing sent to the channel has been received for that long, and past its 300 s threshold on the very first event, so it fired at once rather than after five minutes of real silence. The next outage is now opened by the first restart attempt that actually **fails**, which is the only version that stays correct when the restart *succeeds*; a real outage is dated one backoff delay late (≤60 s) where the eager version's error was unbounded. **The reason it survived the first round is the general lesson: escalation is a log line and nothing else, so the sequence had no test seam at all.** Splitting the pure half out as `note_outage` over a new `Outage{Continues,Ends}` — now the only place either half of the escalator's outage state is driven from — made it observable; two of its three tests fail before the fix (`Some(14400s)` where `None` is required). Two doc defects from the same round: `render_email_help` told operators to query `action IN ('channel.started','channel.boot_failed')` and never learned about `channel.died`, so the documented query silently hid the event this very branch adds (the three names are now substituted from `channel::actions` the way the disabled-log phrase already was, and the test **iterates the set**, so a new action is a failing test — that is #516's drift finding in its other direction, *adding* rather than renaming); and `record_success`'s docs claimed the supervisor calls it "on every successful start", which it does not and must not, since a start proves nothing and resetting there would silence the escalator exactly when it is needed.

**Kastellan survives a reboot on Linux** (`4e1d30ca`, PR [#509](https://github.com/hherb/kastellan/pull/509), closes [#508](https://github.com/hherb/kastellan/issues/508)). `supervisor/src/systemd_user.rs` wrote correct `[Install] WantedBy=` stanzas and then never ran `systemctl --user enable`, so nothing was linked into `default.target` and a rebooted Linux host came up running nothing — while macOS came back, because `RunAtLoad=true` is unconditional in every plist. That parity break is what left a real Matrix message unanswered on 2026-08-02. `install` now enables `<name>.service`; `install_target` enables the **target only** (it is the boot entry point and its own `Wants=` pulls the members in — pinned by a test so a later change is deliberate); `uninstall_target` disables symmetrically; `enable` failures propagate rather than being swallowed. The `Supervisor` trait now carries **"install implies auto-start"** as an explicit cross-platform contract — which stops at *arming* the unit: getting a per-user manager up on a host nobody logs into is the host's job on **both** platforms (linger on Linux, a GUI session on macOS).

**Its retrospective review shipped as [#511](https://github.com/hherb/kastellan/pull/511) (`fba4102c`)** — no bug in #509's fix (the systemd semantics, enable-the-target-only, and disable-before-remove all check out); six findings, five fixed. The load-bearing one: **`write_atomic` staged through a *destination*-derived tmp path** (`path.with_extension("service.tmp")`), so any two concurrent writers of one unit race on a single file — and because `with_extension` *replaces* the final component, a `.target` was staged through `<name>.service.tmp`, the path a like-named `.service` would use. Now one `cfg`-free `supervisor/src/atomic_write.rs`: per-writer `.tmp.<pid>.<n>` name, `create_new(true)` so uniqueness is *enforced* rather than assumed (a pre-planted symlink is refused, not followed), cleanup on every failed-publish path. The same destination-derived pattern was then found one layer up in `core/src/install/run.rs` (`copy_exec`, `symlink_replace` — the latter `remove_file`d the shared staging path first, deleting the *other* writer's staging link) and fixed the same way.

**PR [#516](https://github.com/hherb/kastellan/pull/516) — MERGED 2026-08-04 as `a21f8276`, closing [#514](https://github.com/hherb/kastellan/issues/514) and [#502](https://github.com/hherb/kastellan/issues/502).** Channel bring-up was one-shot: `main/{matrix_boot,email_boot}.rs` tried once and returned `None` on any failure, so a blip in the daemon's first seconds left the bot **deaf for the life of the process** — every unit `active`, Postgres healthy, and nothing further in the log *because there was nothing to log*. Live on the DGX 2026-08-03 19:07 → 08-04 07:22 (**12 h**; three messages sat queued on the homeserver and were ingested within one second of a manual restart), and `channel not started` also appears 2026-06-21 ×3, 07-02 ×2, 07-12. The trigger was **not** the homeserver: the user manager was itself shutting down (`exit.target has 'start' job queued`), so `systemd-run --scope` could not create the sidecar's cgroup.

The fix is the shape already used one layer down by `PersistentWorker`: a reusable `channel::boot_supervisor::ChannelSupervisor` retrying with the existing pure `RestartBackoff` (1 s → ×2 → 60 s cap), unbounded. Four things are worth carrying forward:

1. **A retry loop needs a fatal class or it is a different bug.** `BootOutcome{NotConfigured|Started|Retry|Fatal}` asks one question per attempt — *could a later try succeed with the same process environment?* `forced_localhost_homeserver` (#459) and a partial `EmailConfig` are `Fatal`: retrying them forever is precisely the respawn loop those checks exist to prevent. Both are test-pinned.
2. **It forced [#502](https://github.com/hherb/kastellan/issues/502) closed.** Every spawn path builds a bare `SidecarHandle` and only wraps it in the `Drop`-bearing `EgressSidecar` *after* the worker also spawns; on the error path `?` dropped the bare handle and `std::process::Child` does not kill on drop. One-shot bring-up leaked at most one proxy — **unbounded retries would leak one per attempt, ~1/min for the length of an outage.** `SidecarHandle` now has the `Drop` its own comments already claimed.
3. **Ordering inside the loop is load-bearing, twice.** Shutdown is checked *before* starting an attempt (else a shutdown mid-backoff spawns a worker that is immediately abandoned), and the attempt branch is `biased` **first** in the select (else an already-completed bring-up could be discarded in favour of shutdown, dropping a `Started` channel without stopping it and leaking the bus's detached tasks).
4. **Two issue suggestions were declined, with evidence.** `After=network-online.target` (item 3) is inert in a `systemd --user` manager — verified live: `systemctl --user list-unit-files | grep -i network` returns nothing on the DGX, so it would order against a unit nothing activates, and it would not have addressed the observed manager-shutdown trigger anyway. `kastellan-cli status` (half of item 2) needs DB-backed state because the CLI is a separate process; what shipped instead is `channel.started` / `channel.boot_failed` audit rows plus a pure `DowntimeEscalator` that escalates once a channel has been down past 5 min and repeats every 30, so a capped-out backoff neither spams nor goes silent. Both written up on the issue.

Bring-up also no longer runs inline, so daemon startup can no longer spend up to 60 s inside the Matrix login before reaching the email channel.

**A host reboot is a reliable reproducer — confirmed live, 2026-08-04 00:02 UTC, on the still-deployed pre-fix build.** The DGX rebooted; the matrix worker's initial sync failed with `tunnel error: unsuccessful` (the egress CONNECT, before the network stack was up), `matrix_boot` logged `channel not started`, and the bot sat deaf with every unit `active` until a manual restart at 00:06 — which succeeded **on the first try**. That error string is *literally* one of the scripted `Retry` outcomes in this branch's own supervisor test, so under the fix it would have been two `channel.boot_failed` rows and `channel.started { attempts: 3 }`. This is a **second independent trigger** alongside the restart-window cgroup race in the issue, and it makes the `Retry` arm's coverage less theoretical than the synthetic tests alone suggest. **Both fixes are now on `main` AND deployed (2026-08-05, `3932672a`), so neither a reboot-window bring-up failure nor a post-boot pump death is a restart case on the DGX any more.**

**Review round (2026-08-04) — the finding was not in the supervisor.** It was that **renaming a log line silently breaks everything that greps for it**, and three things did. Worth carrying forward as a class, not three incidents:

1. **`scripts/upgrade_from_git.sh`'s post-deploy check had gone blind.** It matched `matrix channel bus running` and `matrix worker spawn/login failed`; #514 moved the channel name out of the *message* into a structured `channel` field and turned the second into an anyhow *context* (so it lands in the `error` field, not `"message"`). Now matches `"channel":"matrix"` **plus** the new messages on the same JSON line, and since bring-up is retried it **polls** (`CHANNEL_WAIT`, default 45 s ≈ 1+2+4+8+16 s of backoff plus slack) instead of reading one snapshot, distinguishing `CHANNEL DISABLED` (fatal, exit 1 immediately) from still-retrying. ### The four faults (2026-08-02)

Driven end-to-end from a real Matrix message ("what was my most recent qantas flight booking (in my email)?"). **Four independent faults, only one of which was a kastellan bug in the layer everyone suspected.** Order matters — each masked the next.

1. **Host: the NVIDIA driver was gone.** An `apt upgrade` installed kernel `6.17.0-1029-nvidia` but left `linux-modules-nvidia-580-open-nvidia-hwe-24.04` pinned at `-1021`, so no `nvidia.ko` existed and **Ollama silently ran the 26B model 100 % on CPU** (`/api/ps` → `"size_vram": 0`). The decoy: `linux-modules-nvidia-**fs**-…-1029` (GPUDirect Storage, *not* the driver) *did* upgrade, so the package tree looked current. **Diagnose in one line before blaming kastellan:** `ssh dgx 'lsmod | grep -c nvidia; curl -s 127.0.0.1:11434/api/ps | grep -o "size_vram[^,]*"'`. Memory: [[dgx-apt-upgrade-drops-nvidia-module]].
2. **Deployment: kastellan did not survive a reboot on Linux.** The missing `systemctl --user enable` — **fixed 2026-08-03 in PR [#509](https://github.com/hherb/kastellan/pull/509)**, see Current state. The DGX had been hand-`enable`d as a workaround, so its units already read `enabled`; a fresh install elsewhere had the bug until this landed.
3. **`llm-router`: the local reasoning model thought until the request timed out.** On the real ~16 k-token planner prompt the 26B model produced **15 094 chars of `reasoning` for 1 519 chars of plan**, 222 s wall clock; inside the daemon the same call consumed a full **600 s** budget and still timed out, so **raising `KASTELLAN_LLM_TIMEOUT_MS` is NOT a fix** (tried, failed, task 119). Fix: `ChatRequest.chat_template_kwargs` + `RouterConfig::disable_thinking` (default ON, `KASTELLAN_LLM_DISABLE_THINKING=0` opts out) emitting `{"enable_thinking": false}`, the OpenAI-compat extension both Ollama and vLLM honour, applied in `dispatch_local` as a property of the local leg; an explicit caller value wins; unset ⇒ field not serialised ⇒ byte-identical payload. Measured **222 s → 51 s**. There is no `chat_template_kwargs` PARAMETER in Ollama Modelfiles (`PARAMETER think false` is rejected — thinking lives in `RENDERER`/`PARSER`), so no zero-code operator workaround exists. Suppression *reduces* the reasoning block rather than eliminating it (15 094 → 1 933 chars), so headroom under the 180 s cap is real but not unlimited.
4. **`plan_parser` — the one that hid everything else.** `parse_plan_lenient` re-emitted the **strict**-path error whenever the lenient path failed, "so callers see a stable error type". The strict path parses the whole raw response, so its error always describes the markdown fence: `expected value at line 1 column 1` — i.e. *"your output wasn't JSON."* The model was in fact returning **complete, correct, well-formed fenced plans** that merely omitted a required field; the real error was `missing field 'steps'`. Every reader, human and agent, was pointed at the fence, at empty completions, at context overflow — none of which were happening. **Cost the entire session** until the raw output was finally logged. The lenient error is now returned whenever the input contained a `{`; the strict error survives only for input with no `{` at all, where "not JSON" is honest.

**Also fixed:** `AgentError::Decode` captured the raw completion but its `#[error("plan decode failed: {detail}")]` Display renders only `detail`, so the one piece of evidence needed reached nobody. The structural facts (`detail`, `raw_len`, `has_brace`, `finish_reason`, token counts) are now logged — that is what broke the case open. The 600-char raw head sits at `debug!`: a planner completion restates recalled memories and prior step output verbatim, so on a mail task it *is* the user's correspondence, and the daemon log (`~/.local/state/kastellan/*.out`) is a plaintext file with none of `audit_log`'s role gating — `docs/threat-model.md` gained a **"User data in the daemon log"** subsection stating the rule. **`steps` is deliberately NOT defaulted** — an empty `steps` marks a terminal plan, so defaulting it would turn a *truncated* plan into a silently-terminal one.

### The fail-open `data_ceiling` correction

`data_ceiling` is a **ceiling**, so the most *sensitive* `DataClass` is the most *permissive* value it can hold. #505 defaulted an absent field to `Secret` and shipped it documented as fail-**closed**; `Secret` is rank 3, the maximum. The field has exactly two enforcement points, both in `cassandra/deterministic.rs`: **I1** (`ceiling >= floor`) can never fire at rank 3 whatever the floor, and **I3** (`step.classification <= ceiling`) can never fire because no step class outranks it. A plan omitting the field is therefore **not ceiling-constrained at all** — where it was previously rejected outright.

Severity is bounded and worth stating precisely: I1/I3 only ever catch a model contradicting *its own* declarations (a competence signal, not an attack barrier — a hostile planner would declare a matching high ceiling). **The second review round narrowed the "I2 is still enforced" claim**, which was too broad: an `invoke_skill` plan's steps are *not* model-written — L3 expansion stamps each expanded step's `classification` with `plan.data_ceiling` (`memory::l3_invoke::agent` / `l3py_invoke::agent`) and runs at `inner_loop` step 1b, **before** the reviewer at step 2 — so on a plan that both omits the field and invokes a pinned skill, the expanded steps carry rank 3 and I2 passes vacuously for them too: **all three invariants, not two**. Nothing outside `deterministic.rs` reads `step.classification`, so the effect stays inside that review stage. A defect in a defence-in-depth layer, not a hole in the threat-model boundary. Behavioural fix: [#506](https://github.com/hherb/kastellan/issues/506).

### Egress / MITM traps (from #491–#503) — read before touching the proxy

1. **A `CA:TRUE` self-signed *leaf* is rejected at handshake** with rustls' `CaUsedAsEndEntity`, even though `openssl verify` accepts it — and `openssl req -x509` commonly produces exactly that shape. It fails **late and opaquely** as a `mitm_failed: …` egress decision, not at startup. The live DGX localmail cert WAS this shape; regenerated `CA:FALSE` on 2026-07-26 (backups `~/.config/localmail/tls/*.cabak-20260726-173651`) and the tier then passed. Working shapes: a non-CA leaf (`CA:FALSE`) or a real CA that signed a separate leaf. Verify with `openssl x509 -in <cert.pem> -noout -text | grep -A1 'Basic Constraints'`.
2. **The upstream anchor is trusted for EVERY host that sidecar can reach**, not just the keyed origin. #492 therefore *enforces* single-private-origin rather than trusting operator discipline: an anchor is handed out only when the worker's allowlist resolves to a single private origin written as an **IP literal** (privateness via `kastellan-net-classify::is_denied_range`, the proxy's own SSRF predicate, so the two can't drift), and **a refusal fails the spawn**. **Known limitation, documented and test-pinned, not closed:** keying is per-**host**, not per-service, so two private services sharing one address (the DGX's actual shape: localmail `:8443` + SearxNG `:8888` on `10.0.0.3`) are one origin to the rule and the second worker's sidecar also receives the first's anchor. Closing it needs `host:port` keying or a per-host rustls verifier (#492's explicit non-goal); mitigation is operational — give co-located private services distinct addresses.
3. **`tls_intercepted: true` is weaker than it reads** — emitted when the proxy takes the MITM branch, *before* the upstream handshake. **Round-tripped bytes are the load-bearing assertion.**
4. **The decision-ingest thread is deliberately DETACHED**, so reading captured rows right after `worker.close()` races its drain — worst for a connection's LAST decision. Any test asserting on a *terminal* egress decision must poll to quiescence (the shared helper does).
5. **UDS path length:** a merely descriptive scratch-dir prefix under macOS `$TMPDIR` pushes `<scratch>/egress.sock` past `sun_path` (`SUN_LEN` error) and the sidecar dies before reading the CA. Use `tests-common::short_scratch_root`.
6. **The proxy's upstream leg trusts webpki roots ONLY** unless the operator sets an anchor — so **no hermetic self-signed origin is possible for a MITM'd worker's e2e**; real-origin tiers are structural, not lazy ([[egress-proxy-upstream-trusts-webpki-only]]).
7. **Egress-decision assertions must match `host:port`, not a bare host** — a bare-host check passes on any decision mentioning it, and on the DGX loopback SearxNG and the embed endpoint share an address (cost a #448 round-trip; the convention is `is_allowed_row_for` / `is_for_origin`).

### Process lessons that have each cost a re-run

- **Write long-run logs to `$HOME`, never `/tmp` — on BOTH hosts.** `/tmp` is scrubbed mid-run on the DGX *and* on the Mac; macOS deleted a completed `cargo test --workspace` log plus the harness task-output files, forcing a second 45-minute gate. Include an explicit exit-code line and a DONE sentinel. [[dgx-run-logs-tmp-scrubbed]]
- **Each host is structurally blind to the other's `cfg` arms.** Mac clippy compiles `#[cfg(target_os="linux")]` items out, so an unused cfg-linux helper passes on the Mac and fails the DGX `-D dead-code` gate; the mirror direction is real too (the DGX is blind to DE-gated items in dual-platform files). Gate both hosts after scripted edits. [[cfg-linux-e2e-deadcode-dgx-clippy]]
- **Don't race sidecar tests against a build.** The 5 s sidecar-readiness budget is load-sensitive: `email_mitm_e2e` took 28.6 s loaded vs 8.2 s quiet, and `egress_force_routing_e2e::forced_coupling_…` fails under full-workspace load but passes 3/3 standalone in ~0.11 s. **Don't "fix" it by inflating a production timeout.** Adjacent: [#328](https://github.com/hherb/kastellan/issues/328). (The *leaked* sidecar children were a different thing — #502, fixed in PR #516.)
- **Mac CLI cargo blocks on the IDE's rust-analyzer** holding `target/debug/.cargo-lock` — use a scratch `CARGO_TARGET_DIR` (e.g. `$HOME/.cache/kastellan-sdd-target`) or iterate on the DGX. Never pipe background cargo through `| tail` (masks the exit code, buffers output). [[mac-cargo-buildlock-prefer-dgx]]
- **Verify deployment claims before carrying them forward** — issue comments and handovers go stale; check the live host before repeating a claim in a spec, PR or ROADMAP. [[handover-claims-verify-before-carrying]]

#### What CI does not cover

`linux-check.yml` is **compile-only** — `cargo check --workspace --all-targets`, `clippy -D warnings`, and `cargo test -p kastellan-tests-common` (hermetic structural guards only). The workflow header argues that scope deliberately, and it is the right default. But it means a green PR check says *nothing* about behaviour, and two consequences are worth holding in mind rather than rediscovering:

- **`cargo test -p kastellan-supervisor` never runs on a PR.** So #508's regression guard — the tests pinning that `install`/`install_target` actually call `systemctl --user enable` — is enforced only by an operator running the DGX suite. Both tests are `cfg(target_os = "linux")` *and* `[SKIP]` without a live user manager, which `ubuntu-latest` does not have, so simply adding the job would not fix it. [#510](https://github.com/hherb/kastellan/issues/510) tracks the options (a `REQUIRE_USER_MANAGER=1` knob first, then a runner that can satisfy it).
- **There is no macOS job at all** — `.github/workflows/` is `linux-check.yml`, `docs.yml`, `release.yml`. So for `cfg(target_os = "macos")` code the gap is not "never run", it is **never compiled**: the launchd backend, its tests, and every macOS arm of a dual-platform file are invisible to CI, and the Mac is the only host that sees them (the mirror of [[cfg-linux-e2e-deadcode-dgx-clippy]]). That is the concrete reason #511 folded the two backends' staging helpers into one `cfg`-free module: shared code gets compiled and tested on a PR, per-backend code does not.
- **The one lever that does work: `tests-common`.** Its unit tests *are* run on every PR, which makes it the right home for hermetic *structural* guards over things CI otherwise cannot see — the provisioning sha256 pins, and since #504 the installer-coverage guard (`installable.rs`) that fails when any binary the workspace builds is neither installed nor explicitly exempted. If a defect's character is "survives every check not specifically looking for it", that crate is where the check belongs.
- More generally, **any invariant whose only guard is an integration test is DGX-gated**, and integration tests that skip-as-pass are indistinguishable from tests that ran. The #508 arc is the worked example of why that matters: correct-looking code, green everything, broken only after a reboot nobody performs during development.

**Standing macOS test-infra gotcha (not a regression):** a *full-workspace* run under `KASTELLAN_PG_BIN_DIR` flakes ~4 tests in `core/tests/embedding_recall_e2e.rs` at PG bring-up (`tests-common/src/pg.rs`) — parallel `initdb`/launchd churn (issue [#130](https://github.com/hherb/kastellan/issues/130) territory); they pass single-threaded and in isolation. Use skip-as-pass for the whole workspace on the Mac and run live-PG suites individually or on the DGX. Two `error[E…]` blocks in a full log are the **expected output of two pre-existing `compile_fail` doctests** (`Lifecycle::IdleTimeout` non-exhaustive, `WorkerCommand::new` private), both reporting `... ok` — not failures.

## Key design decisions locked in

- **Vendor-neutral, AGPL-compatible deps only.** Apache-2.0 / MIT / BSD / MPL / LGPL / (A)GPL fine; CDDL, BUSL, SSPL, Elastic and "source-available" are blocked.
- **Cross-platform first-class.** Linux (DGX Spark primary) + macOS. No Linux-only code without a macOS counterpart of equivalent guarantee.
- **Rust core, Python only inside sandboxed workers.** No PyO3, no in-process Python; the core never executes untrusted code in-process.
- **One process per worker, one OS sandbox per worker.** No "spawn unsandboxed" escape hatch in `tool_host` — don't add one.
- **Hybrid LLM with policy routing.** Local-first over OpenAI-compatible HTTP; Frontier only via the Phase-5 policy gate, through the egress proxy.
- **Single-host deployment via OS-native user-level supervisors** (`systemd --user` / launchd). No k3s.
- **Fixed core tools, sandbox-bound agent-authored Python.** Named/persisted skills get a human-approve gate (the L3 arc).
- **JSON-RPC 2.0 over stdio** — MCP-stdio compatible, so a richer MCP client can be swapped in without moving the trust boundary.
- **The operator→daemon command channel is the Postgres `tasks` queue + `LISTEN/NOTIFY`**, not a new IPC socket. `ask` and `memory l3 run` both ride it (#179 Opt-3).
- **Threat-model invariant:** worst-case compromise reaches *at most* the agent's own OS user, its own Postgres role, its own scratch FS, and the allowlisted endpoints for the *one* compromised tool. Nothing else.

## Inspirations / things to read before each milestone

Two adjacent OpenClaw-derived projects ship AGPL-compatible code worth reading before a new milestone:

- **ZeroClaw** ([`zeroclaw-labs/zeroclaw`](https://github.com/zeroclaw-labs/zeroclaw), 100 % Rust) — [`crates/zeroclaw-runtime/src/security/`](https://github.com/zeroclaw-labs/zeroclaw/tree/main/crates/zeroclaw-runtime/src/security) has working `bubblewrap.rs`, `landlock.rs`, `seatbelt.rs`, `pairing.rs`, `webauthn.rs`, `leak_detector.rs`. **Don't copy its in-process tool model** — tools run as in-process Rust traits with the OS sandbox around the whole runtime, a weaker boundary than process-per-worker.
- **IronClaw** ([`nearai/ironclaw`](https://github.com/nearai/ironclaw)) — read its dispatcher chokepoint pattern (`ToolDispatcher::dispatch()` as the single audit/safety funnel for every action). Drawbacks: WASM-as-boundary is software-only containment; the Postgres+libSQL dual backend is overkill at our stage.

The *defining* architectural difference: kastellan enforces **one OS process + one bwrap/Seatbelt jail per worker**. Both reference projects retreated from that. Don't.

## How to update this document at session end

**Header first, prose last.** The header is what the next session treats as authoritative; stale header fields mislead silently even when the prose is right.

1. **Bump the header before writing any prose:** `Last updated:` → today; `main` HEAD → `git log --oneline -1`; `Last gate:` → the passed/failed/ignored/`[SKIP]` counts from a fresh `cargo test --workspace`. Then fix **every test count embedded elsewhere that changed** — a fresh agent greps for them and trusts whatever it finds.
2. **Move the picked TODO into [Recently merged](#recently-merged)** with enough detail (file paths, why-not-X, gotchas, count delta) to start cold, and update the [Test baseline](#test-baseline-authoritative) table.
3. **Write a fresh [Next TODO](#next-todo)** with options sized for one session each — file paths, gotchas, verification step.
4. **Refresh [Working state](#working-state)** — anything new, anything that became real.
5. **Tick the matching ROADMAP items** with the commit hash.
6. **Commit both files together** with a `docs(handover): …` message.
7. **If a milestone shipped:** does `site/roadmap.html` (timeline + "Last updated" stamp, and the landing-page status numbers) need a one-line update? See `site/README.md`.

### Pruning convention

This file stays focused on **what the next session must act on**: current state, the last 2–3 sessions, and the next TODO. Prune when it grows past what a fresh session can absorb cold — judge by *reading weight*, not line count; the 2026-08-03 prune was triggered at 546 lines / ~73 k tokens.

1. **Snapshot first** — copy to `archive/handover_<YYYYMMDD>[_<slug>].md`. The archive is the audit trail: never edited after the fact, never deleted.
2. **Keep:** the header, "Read these first", "Working state" (current truth), the most recent 1–2 sessions, "Key design decisions", "Next TODO", open issues, open questions, "Inspirations", and this section.
3. **Compress everything else** into one bullet per session, or into the archive pointer if it is no longer load-bearing.
4. **Cross-link** every compressed bullet to the archive snapshot.
5. **Commit the prune separately** (`docs(handover): prune older sessions, archive pre-prune snapshot`) so the diff is reviewable.

The archive directory is the historical record; this file is the working brief.
